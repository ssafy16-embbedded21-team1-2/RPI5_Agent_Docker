# 장비 정보 기반 검증

기준일: 2026-11-13. 회의 결정에 따라 **장비 정보를 충분히 확보한 환경에서 진단을 검증**한다.
장비·펌웨어·통신 명세·정상 기준을 고정하고 기대 결과와 실제 관측을 비교한다.
미확인 장비 접수·미지 로그 파싱·규약 추정은 후속 범위다.
정보가 충분해도 수집 실패·미지원·손상·SWD 접근 제한은 발생할 수 있으므로 기존 오류·유효성 계약을 유지한다.

## 1. 이번에 구현한 범위

실제 보드 없이 기존 가상 벤치를 검증하는 기준 명세와 케이스 비교 API를 추가했다.

| 항목 | 구현 |
| --- | --- |
| 판정 기준 | `specification.py`의 고정 `fixture-bench-v1` |
| 타임아웃 | 게이트웨이 500ms, BMS 원본 1000ms. age가 한도보다 클 때 지연, 같으면 최신 |
| 기준 소유 | 수집 데이터가 아닌 코드. 요청 본문으로 변경 불가 |
| 케이스 | `verification.py`의 `fixture-acceptance-v1`, 기존 13종 시나리오의 기대 finding code 목록 |
| 명세 조회 | `GET /verification/specification` |
| 케이스 실행·비교 | `POST /verify`. 기존 `/diagnose`의 수집·판정·선택 설명 흐름을 그대로 실행한 뒤 비교 |
| 결과 식별 | `/diagnose` 결과에도 `assessment_specification_id` 추가 |
| 공급자 제한 | 기본 내장 공급자에서만 `/verify` 가능. 다른 공급자는 수용 기준이 없어 HTTP 409 |

이 시간 한도는 기존 가상 데이터에 사용하던 값을 코드 명세로 옮긴 것이다.
팀의 실제 CAN ID·DBC·ECU 주기·타임아웃·DID를 확정한 것이 아니다.
장비별 물리 식별·버전 일치 검사는 아직 구현하지 않았다. 명세 ID도 실제 보드의 식별값을 대체하지 않는다.

기존에는 `gateway.snapshot.data`가 `gateway_timeout_ms`, `bms_timeout_ms`도 제공했다.
이제 가상 공급자는 age와 유효성만 제공한다. 외부 공급자가 예전 한도 필드를 보내도 판정에서는 무시한다.
한도를 조회하던 클라이언트는 새 명세 조회 API를 사용해야 한다.
LLM 입력에서도 관측 데이터의 한도 필드는 제거하고 별도의 기준 명세를 전달한다.

## 2. 실행 방법

기존 실행 환경에서 서버를 시작한 후 PowerShell에서 호출한다. 기본 요청은 LLM을 사용하지 않는다.

```powershell
Invoke-RestMethod http://localhost:8000/verification/specification

$requestBody = '{"scenario":"bms_timeout","use_llm":false}'
$result = Invoke-RestMethod http://localhost:8000/verify `
  -Method Post -ContentType 'application/json' -Body $requestBody
$result | ConvertTo-Json -Depth 15
```

기본 공급자의 모든 케이스를 실행할 때:

```powershell
$catalog = Invoke-RestMethod http://localhost:8000/verification/specification
foreach ($case in $catalog.cases) {
    $requestBody = @{ scenario = $case.case_id; use_llm = $false } | ConvertTo-Json
    $result = Invoke-RestMethod http://localhost:8000/verify `
      -Method Post -ContentType 'application/json' -Body $requestBody
    [pscustomobject]@{ Case = $result.case_id; Verdict = $result.verdict }
}
```

`/verify`는 `/diagnose`와 같은 진단 동시 실행 슬롯과 LLM 활성화·모델 선택 정책을 사용한다.
`use_llm=true`이면 설정된 모델을 실제 호출할 수 있으므로 필요할 때만 지정한다.
실행 결과의 영구 저장·반복 성능 집계는 아직 자동화하지 않았다.

## 3. 결과 해석

| 필드 | 의미 |
| --- | --- |
| `scope=fixture_findings` | 가상 케이스의 코드 판정 목록 비교 |
| `case_catalog_id`, `case_id` | 비교한 케이스 목록 버전과 시나리오 |
| `verdict=passed` | 기대 code와 실제 code가 같고 중복도 없음 |
| `verdict=failed` | 기대 code 누락·예상 밖 code·중복이 존재 |
| `verdict=not_evaluated` | 비교 함수에 전달된 판정 명세 ID가 케이스의 명세와 다름 |
| `missing_finding_codes` | 기대했지만 없는 code |
| `unexpected_finding_codes` | 기대하지 않은 code |
| `duplicate_finding_codes` | 중복 출력한 code |
| `physical_validation=false` | 실제 CAN·보드 시험 결과가 아님 |
| `llm_semantics=not_evaluated` | LLM 설명의 근거 일치는 평가하지 않음 |
| `diagnosis` | 원본 가상 증거·실제 findings·설명/오류 등 기존 진단 결과 |

수집기가 알려진 실패를 정확히 구분하면 그 실패 케이스의 검증은 통과할 수 있다.
예를 들어 `CRASH_RECORD_TIMEOUT` 검증 통과는 크래시 조회 성공이나 장비 정상 판정을 뜻하지 않는다.
이 비교는 code 집합을 대상으로 하며 severity·자유 설명·센서 수치의 모든 속성을 검증하는 것은 아니다.

기대 code는 fixture 생성기나 판정 함수에서 계산하지 않고 별도 목록으로 유지한다.
비교는 모델 설명 생성 이후에 수행하며 케이스 정답·고장 주입 설정을 LLM 입력에 넣지 않는다.
모델에는 관측 증거·코드 판정·정상 한도를 전달한다. 코드가 통과해도 모델은 잘못 설명할 수 있으며,
`generated`는 출력 형식 통과로만 해석한다. 의미 정확성·새 역할별 라우팅 구현은 여전히 후속 범위다.

## 4. 실기기 연결 전에 확정할 것

1. 보드 관리 ID·모델·리비전·펌웨어 Build ID·지원 기능을 등록한다.
2. 실제 CAN 경로·배선·속도·명세/DBC 버전과 정상 기준·경계값을 공동 검토한다.
3. 선택한 케이스의 원본 프레임·기대 디코딩·기대 판정·합의한 고장 주입과 원복 방법을 준비한다.
4. 정상·BMS 원본 갱신 지연·로컬 Bus-Off의 수집 경로부터 연결한다. 필요한 진단 서비스는 이후 확장한다.
5. 실제 공급자의 source/mode·기한·대상/버전 일치 확인·전송 허용 정책을 구현하고 물리 케이스 목록을 별도 등록한다.

셋업 레포의 `docs/장비_정보_기반_검증_계획.md`와 보드 등록·규약 회의 템플릿에 준비 자료·수용 조건을 정리했다.
현재 `/verify`에 물리 공급자를 주입하거나 요청값만 바꿔 실기기 검증을 시작할 수는 없다.
물리 자료가 부족한 시험은 준비 보류로 남기며 임의 바이트 의미나 정상 기준을 LLM으로 채우지 않는다.
CAN FD·다중 ECU·FOC·FFT·자동 복구는 첫 수집/판정 검증 이후의 확장 설계로 유지한다.

## 5. 로컬 확인

```powershell
uv run --frozen pytest -q
uv run --frozen ruff check src tests
uv run --frozen ruff format --check src tests
```

케이스 비교, 한도 경계·수집 데이터 한도 무시, 예상 밖 판정·중복·명세 불일치, 공급자 오인 방지,
모델 정답 비노출과 설명 정확성 미평가 표시를 자동 테스트한다. 기존 수집·라우팅·정책 회귀도 함께 확인한다.
기존 실기기 검증 문서는 당시 배포본의 이력이다. 이번 로컬 변경을 RPi 배포·실모델 재검증 완료로 기록하지 않는다.

2026-11-13 PC 확인 결과:

- Python 자동 테스트 **145개 통과(7.90초)**. 제품/벤치 양쪽의 13종 케이스와 실패·경계·정답 분리 회귀 포함.
- Ruff 검사·포맷 검사 통과.
- 배포용 wheel 빌드 후 해당 wheel에서 직접 API를 불러 **13종 가상 케이스 모두 통과**.
- 실제 Qwen·Pamout·CAN·STM32 호출과 RPi 배포는 수행하지 않았다.
- 원본 확인 기록: `data/known-equipment-pc-verification-20261113.json`(Git 제외).
